# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

HNX-CIS Frontend — a React SPA for the Hanoi Stock Exchange's Listing / Bond Market / Disclosure
management system (Vietnamese-language UI). It is currently in a **frontend-only, mock-data
prototype stage**: almost all entities (organizations, securities, submissions, workflows...) live
in `src/data/*.ts` (`mockData.ts` plus per-area files: `accessMock.ts`, `businessMock.ts`,
`metadataMock.ts`, `roleCatalog.ts`, `dossierForms.ts`, `translationGlossary.ts`) and are mutated
in-memory via React state in `src/App.tsx`. The only wired-up real backend calls are the four
Gemini-powered AI features in `src/services/aiService.ts`. Keep this in mind — most "business
logic" changes should extend the mock data / client-side services rather than assume a live REST
backend exists for that entity yet.

## Commands

```bash
npm run dev       # Vite dev server, http://localhost:5173, proxies /api/* to VITE_DEV_API_PROXY (default http://localhost:8080)
npm run build     # tsc + vite build -> dist/
npm run lint      # tsc --noEmit (this is the only "lint" — there is no eslint/prettier config)
npm run preview   # vite preview --host 0.0.0.0 --port 8080 (serves dist/, mirrors prod)
```

There is no test framework/script configured in this repo. CI (`.github/workflows/ci.yml`) only
runs `npm run lint`, `npm run build`, and a `docker build` sanity check.

Docker/local backend loop:
```bash
cp .env.example .env
docker build -t hnxcis-frontend .
docker run -p 8080:8080 -e API_BASE_URL=https://hnxcis-backend-xxxx.a.run.app hnxcis-frontend
```

## Runtime configuration — never hardcode the backend URL

The backend base URL is **not** baked into the JS bundle. Resolution order (`src/config/runtime.ts`):

1. `window.__APP_CONFIG__.API_BASE_URL` — injected by `/env.js`, which is regenerated by
   `nginx/40-generate-env-js.sh` on every container start from the `API_BASE_URL` env var. This is
   what lets ops repoint the frontend at a new backend (`gcloud run services update ... --set-env-vars API_BASE_URL=...`)
   without rebuilding the image.
2. `VITE_API_BASE_URL` build-time env (rarely used).
3. Empty string → same-origin requests (the Vite dev server proxy handles `/api/*` locally).

`public/env.js` is the dev-mode stand-in for the generated file. Always call the backend through
`src/lib/apiClient.ts` (`apiGet`/`apiPost`) or `src/services/aiService.ts` — never raw `fetch`.
`apiClient.buildAuthHeaders()` auto-attaches the Firebase ID token when a user is signed in; the
backend accepts anonymous calls while its own `AUTH_REQUIRED=false`.

## Architecture

### Portal routing (URL paths, hand-rolled — no router library)

The three portals are three **separate URLs**, not tabs of one page. `src/lib/portalRoute.ts` maps
path → portal, listens to `popstate`, and normalises unknown paths. There is no react-router: the
app has exactly three top-level paths, while navigation *inside* IMS stays state-based
(`activeModule`, dozens of screens). nginx already has SPA fallback, so deep links work in prod.

| Path | Portal | Auth |
| --- | --- | --- |
| `/ims` | HNX staff workspace, gated further by `activeModule` | **Login required** |
| `/icds` | `CorporatePortal` — organization self-service (`corp_dashboard`, `corp_filing`, `corp_history`) | Free |
| `/news` | `PublicCorporateNews` — public news feed | Free |

`/` and any unknown path redirect to `/news` (the public face). Only `/ims` renders `LoginScreen`;
it accepts `actorType === 'HNX'` accounts only and points organization accounts to `/icds`.

There is deliberately **no in-app switcher between the three** — the header shows which portal you
are in, nothing more. Users reach a portal by its own URL, like separate sites.

At `/icds` there is no logged-in user, so `App.tsx` passes a `guestOrgUser` (first `ORGANIZATION`
persona) as `portalUser` for org context; `/news` needs no user at all.
- `activeModule: string` — inside the internal portal, the *prefix* of this string selects which
  module component renders, mirroring the department that owns that function:
  - `dashboard`, `ai_center` → standalone modules
  - `qlny_*` → `ListingModule` (Phòng Quản lý Niêm yết — equities, status control Đ40-44, delisting, fees, corporate actions)
  - `tttp_*` → `BondModule` (Phòng Thị trường Trái phiếu — private/green bonds)
  - `tttt_*` → `DisclosureModule` (Phòng Công bố Thông tin — approval inbox, violations, display config)
  - `admin_*` → `AdminModule` (form/rule builder, user & ABAC permission management)
  - `meta_*` → `MetadataModule`, `access_*` → `AccessModule`, `surv_*` → `SurveillanceModule`,
    `own_*` → `OwnershipModule`, `bond_*` → `BondExtraModule`, `cbtt_*` → `DisclosureExtraModule`,
    `report_*` → `ReportModule`, `survey_*` → `SurveyModule`
  - `uc_*` → `UseCaseRouter` (see "SRS-driven use-case screens" below — a different registration
    mechanism from the other prefixes)

  When adding a new screen for one of the plain prefixes above, follow the convention and wire it
  into both `Sidebar.tsx` (nav entry, gated by role) and the corresponding `startsWith('xxx_')`
  block in `App.tsx`. For a screen that has a formal SRS doc, use the `uc_*` mechanism instead.

- Role gating (`Sidebar.tsx`) uses substring checks on `UserRoleCode` (e.g. `userRole.includes('QLNY')`),
  not a permission table — `ROLE_SYS_ADMIN`/`ROLE_BIZ_ADMIN` and `ROLE_HNX_EXEC` see everything.

### SRS-driven use-case screens (`src/components/modules/usecases/`)

A subset of IMS screens (catalog/lookup management: countries, provinces, wards, departments,
enterprise types, positions, dictionary values...) are built directly from formal spec docs in
`docs/srs/[CODE] <Vietnamese title>.md` and registered separately from the plain `activeModule`
prefixes above:

- `src/lib/imsRoutes.ts` (`IMS_USE_CASES`) is the single source of truth tying together the
  `uc_*` module code, the URL slug (`/ims/<slug>`), the SRS use-case code, and the sidebar
  label/breadcrumb — declared once instead of in three places that could drift apart.
- `src/components/modules/usecases/index.tsx` (`UseCaseRouter`) maps each `uc_*` code to its view
  component; `App.tsx` renders it via a single `isImsUseCaseModule(activeModule)` check rather than
  one more `startsWith('xxx_')` branch.
- Unlike the rest of `/ims` (state-based navigation only), these screens each get a real deep-linkable
  URL: `imsModuleFromPath`/`imsPathForModule` in `imsRoutes.ts` convert between the URL and the
  module code, called from the same `popstate`/history plumbing that drives portal routing.
- `catalogTypes.ts`, `catalogUi.tsx`, and the `useCatalogList` hook factor out what the SRS docs
  specify identically across these screens: the `CatalogRecord` shape (`statusFlg`/`activeFlg`/
  `deleteFlg` numeric flags, not booleans — matches the DB column types verbatim), soft-delete
  filtering, keyword search applied only on submit/Enter (not per-keystroke), default sort by
  `createdDate`, and pagination. Each screen still owns its own `rows` state and add/edit/delete
  logic — only list *behavior* is shared, not data.
- To add a new SRS-backed catalog screen: add an entry to `IMS_USE_CASES`, add the `uc_*` → view
  mapping in `usecases/index.tsx`, and build the view on `useCatalogList` + `catalogUi.tsx` so it
  stays consistent with the others.

### Domain model (`src/types/hnx.ts`)

Every persisted entity extends `BaseEntity`: `id`, `createdAt/By`, `updatedAt/By`, soft-delete
(`deletedAt/By/deleteReason`), and an append-only versioning pair `versionNo`/`isCurrent`. When
mutating an entity in mock data or in new UI, preserve this shape rather than doing plain in-place
field updates — the real backend models history this way (see `AuditLog`, which records
`beforeJson`/`afterJson`/`diffJson` per change).

Key entity families: `Organization` / `SecurityItem` / `EquityProfile` / `BondProfile` (listing),
`Submission` (a disclosure filing, driven through `SubmissionStatus`), `TemplateDefinition` +
`TemplateField` + `FieldDefinition` (admin-configurable dynamic report forms), `WorkflowDefinition`
/ `WorkflowTask` (approval pipeline), `RuleDefinition` / `Alert` (compliance rules, e.g. Điều 40
late-disclosure warnings), `DisclosureObligation` (per-org/per-period reporting deadlines),
`FeeSchema` / `FeeRecord`, `NotificationItem`, `AuditLog`.

### Client-side "business logic" services (`src/services/`)

These are plain singleton classes (not React hooks) that encapsulate rules the UI shouldn't
reimplement inline — treat them as the place logic belongs when it's reused across modules:

- `formEngine.ts` — validates a submission payload against a `TemplateDefinition`'s fields
  (required/type/min/max) and computes a human-readable title from `titleFormula` placeholders.
- `ruleEngine.ts` — scans obligations against `RuleDefinition`s to produce `Alert`s (currently:
  Điều 40 late-disclosure warning past a configurable `MAX_LATE_DAYS`).
- `workflowEngine.ts` — evaluates textual guard expressions on workflow transitions (e.g. fee must
  be `CONFIRMED`, both review+approval timestamps must be set), enforces submitter≠approver dual
  control, and computes task due dates via the business calendar.
- `businessCalendar.ts` — Vietnamese working-day calendar (`HOLIDAYS_2026` seed, weekend + holiday
  + makeup-workday aware) used for SLA due-date math, plus `formatVndWords` (VND amount → Vietnamese
  words, used on printed/legal documents).
- `notificationService.ts` — turns `DisclosureObligation` deadlines into styled badges/cards
  (overdue / within-7-days / normal) and synthesizes `NotificationItem`s for the bell/dashboard;
  "today" is computed from the real clock but the mock data is authored around 2026 dates.
- `aiService.ts` — the one service that hits a real backend (`/api/gemini/*` + `/api/health`),
  wrapping the 4 AI features: `nl2Query` (NL→report query), `dataScan` (financial doc extraction
  vs. declared values), `translate` (VI→EN with glossary), `chat` (FAQ chatbot).

### Shared UI primitives (`src/components/common/`)

Module components compose these rather than building bespoke tables/forms per screen:
`DynamicForm` / `DynamicTable` (schema-driven, fed by `TemplateDefinition`/`FieldDefinition`),
`StatusBadge` (renders `SecurityStatus`/`SubmissionStatus`/`BusinessCaseStatus` with Vietnamese
labels + color coding — extend its switch statements rather than inlining new status colors
elsewhere), `WorkflowActionBar` (approve/reject/transition controls tied to `workflowEngine`),
`AuditHistoryModal` (renders filtered `AuditLog` entries for one entity, opened via
`onAuditHistory(type, id, label)` callbacks threaded down from `App.tsx`).

### Build/deploy specifics

- Path alias `@/*` → `src/*` (both `tsconfig.json` and `vite.config.ts`).
- Tailwind 4 is wired through the `@tailwindcss/vite` plugin — there is no `tailwind.config.js`.
- Production is a static build served by nginx (`Dockerfile`, `nginx/default.conf.template`) on
  Cloud Run; `nginx/40-generate-env-js.sh` regenerates `/env.js` from container env vars at every
  cold start, and `/healthz` is exposed for uptime checks.
- `.github/workflows/deploy-cloudrun.yml` (push to `main`) builds the image, pushes to Artifact
  Registry, deploys to Cloud Run, and verifies `/healthz` + `/env.js` post-deploy. After the
  frontend URL changes, the backend's `CORS_ORIGINS` needs updating too (separate `hnxcis-backend` repo).
- `firebase-applet-config.json` is the public Firebase Web config (safe to be public by Firebase's
  own design); real access control is enforced by Firebase Auth + Security Rules server-side.
